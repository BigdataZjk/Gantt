# 排一下技术选型建议

这份方案待用户决定。当前仓库仅整理 UI 和跨设备交接资料，尚未创建正式应用工程。

推荐组合是 Rust、Axum、React、TypeScript、Vite、SQLite。若用户更倾向 Vue，前端可换 Vue 3，其余结构不变。

## 前后端职责

Rust 与 React、Vue 不属于同一层：Rust 负责后端、数据和权威排期规则；React 或 Vue 负责页面、交互与动画。正式交付保持一个后端进程，由它同时提供网页、接口和实时更新。

| 组合 | 优点 | 取舍 |
| --- | --- | --- |
| Rust + Axum + React + SQLite | 当前大量 21st 参考本身是 React，移植交互和动效直接；服务端可编译交付，数据保留本地文件 | TSX 需按领域合理拆分，避免单个组件包揽全部状态 |
| Rust + Axum + Vue 3 + SQLite | Vue 单文件组件能把模板、逻辑、样式集中，结构直观；部署形态相同 | React 参考组件需要转换，部分动效需要重新核对 |

两者均足够胜任当前工具。不能凭框架名保证哪一个甘特图必定更快；渲染结构、更新范围、拖拽策略和数据访问方式更关键。

## 推荐基础组件

| 层 | 建议 | 理由 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite，或 Vue 3 + TypeScript + Vite | 静态构建适合本地内网工具，开发与生产职责明确 |
| 交互基础 | 按需使用 Radix 类基础组件或 Vue 对应方案 | 复用弹层、焦点、键盘交互，最终样式仍按已确认草案 |
| 甘特图 | 自定义连续条段 + CSS/SVG 背景和标记，数据增大时虚拟列表 | 现有 HOLD、并行、非工作日、双击补排期和顺排约束较特殊 |
| 动画 | CSS、Web Animations，必要处按需使用 Motion | 维持现有动效，不引入完整动画依赖来替代简单效果 |
| 后端 | Rust + Axum + Tokio | 同一进程处理接口、静态网页、鉴权和事件推送 |
| 数据访问 | SQLx，限定 SQLite 相关功能 | 参数化 SQL、连接管理和事务；避免为本项目叠加多个数据库访问层 |
| 数据库 | SQLite | 本地持久文件，无需另装数据库服务器 |
| 实时更新 | SSE + 在线心跳 | 编辑仍通过普通 HTTP，服务端推送数据变化、在线状态与强制退出 |
| 会话 | 服务端 session + HttpOnly Cookie | 记住登录，并能立即撤销停用账号的会话 |

## 高性能要落实的事项

1. 甘特图不为每个需求创建一整年的 365 个复杂交互组件。尽量使用定位条段、轻量网格、稀疏标记；只渲染可视行，缩小时减少刻度。
2. 拖动与缩放通过 requestAnimationFrame 更新。鼠标移动时只做前端预览，松开并正式提交时才写数据库和审计日志。
3. 排期算法放在 Rust 的一个核心模块，服务端计算是权威结果。前端做即时预览，提交时再次校验节假日、调休、分段、人天和不允许的段内交叠。
4. SQLite 开启 WAL、foreign_keys，配置 busy_timeout，事务保持短。多个用户同时修改同一需求时通过 revision 防止静默覆盖；批量顺排用同一个事务验证并应用。
5. 静态资源本地打包，不依赖运行时 CDN。图标、预设头像、日历数据均可随发行包内置。
6. 使用当前稳定且已修复已知 WAL 问题的 SQLite 版本，并在锁文件中固定依赖；不要假定所有系统预装的 SQLite 都相同。

SQLite WAL 支持读写并行，但同一数据库同一时刻只有一个写事务。本项目少量多人、短编辑事务的场景适合它。数据库放在服务端电脑本地磁盘，其他人访问 HTTP，不直接共享数据库文件。

性能结论以正式构建后的体积、内存、拖拽和大数据量测试为准，不预先承诺固定的 MB 数或帧率。

## 精简目录建议

按领域集中代码，不按每个按钮或表单字段建一层目录。下列是正式工程建议，不是已经生成的工程：

```text
Gantt/
├── Cargo.toml
├── Cargo.lock
├── package.json
├── pnpm-lock.yaml
├── vite.config.ts
├── tsconfig.json
├── start.sh
├── README.md
├── src/
│   ├── main.rs          # 启动、服务装配、静态资源
│   ├── api.rs           # HTTP 接口及输入输出
│   ├── auth.rs          # 账号、权限、session、密码
│   ├── db.rs            # SQLite 连接、查询、数据库升级
│   ├── schedule.rs      # 日历、人天、分段、顺排
│   ├── history.rs       # 操作记录、撤回、手动快照
│   └── schema.sql      # 初始表结构
├── web/
│   ├── index.html
│   ├── main.tsx         # 入口、导航与页面装配
│   ├── Gantt.tsx        # 时间轴、条段、交互、缩放
│   ├── Requirements.tsx # 需求池和归档共享列表
│   ├── RequirementPanel.tsx
│   ├── Settings.tsx     # 设置中的五个领域
│   ├── ui.tsx           # 共用弹层、标签、颜色与密码控件
│   ├── model.ts         # 数据类型、请求与共享状态
│   └── styles.css       # 主题变量、整体样式
├── data/                # 运行时创建，不默认提交真实数据
│   └── paiyixia.db
└── handoff/             # 已确认设计与跨设备资料
```

Vue 方案将相应 TSX 文件改为 Vue 单文件组件即可。测试按领域集中，核心算法测试可与 Rust 模块放在同一文件的测试模块中；端到端测试集中为少量测试文件。不要为了压文件数把所有模块塞回一个几千行的文件。

node_modules、target、dist 是可重新生成的构建产物，不是需要手动维护的项目层级，也不提交 Git。

## 数据组织

建议使用稳定 ID，而不是以用户名、业务域文本作为关联主键。数据库至少覆盖：账号与 session、需求、排期段、每日标记、业务域、公共快照、公共操作日志、个人偏好及日历工作日信息。

提需人和项目保持普通字段；统一名称时直接事务更新需求池和归档，不额外增加别名映射系统。状态为固定内部枚举，可显示中文。

GIF、头像等小文件可先保存为数据库 BLOB，保留原始格式及 MIME，减少散落的文件；若后续附件明显增多，再评估独立附件目录。

日志只保留最近 200 条，对最近 50 条有效数据变更保存逆操作资料。手动版本保存数据快照，两者分别实现。账号、密码、权限不参与需求快照恢复。

## 发行与启动

开发时需要 Node/pnpm、Rust 和构建工具；用户部署预编译发行包时不需要安装这些开发工具。

前端先构建，再嵌入 Rust 可执行程序。Mac Apple Silicon、Mac Intel、Linux x64/ARM 按目标平台分别编译，交付对应文件。

```sh
./paiyixia --host 0.0.0.0 --port 8080 --data ./data/paiyixia.db
```

首次运行初始化数据库，初始超管张金科的密码由用户设置。启动脚本只是便利入口，不承载业务逻辑。

运行目录主要为可执行程序和 data/paiyixia.db。WAL 模式运行时可能出现 .db-wal、.db-shm 辅助文件；它们是 SQLite 的正常工作文件。搬迁运行中数据库应使用一致性备份或先正常停服，不能只随意复制主文件。

## 建议推进顺序

1. 用户确认 React 或 Vue、后端数据库组合、密码存储与可见规则。
2. 建立服务端与前端最小工程，打通同端口网页、SQLite 和首次启动。
3. 先实现账号、权限、session，以及需求新增、编辑、归档、只读详情。
4. 完成日历与排期核心，针对调休、跨假期、多段、HOLD、顺排约束、删除最后一段和并发写入做验收。
5. 对照当前 UI 完成甘特图交互、配色、GIF、在线用户与个人偏好。
6. 完成公共版本、200 条操作记录和 50 条撤回边界，验证事务恢复。
7. 在 Mac、Linux 上验证发行包、升级、迁移和一键启动，再给最终交付。

## 需要用户决定的密码取舍

用户已要求超管可查看任意人的现有密码。采用只存 Argon2id 哈希的方案时，无法读取原密码，只能重设；这需要用户同意调整原约定。

若保留查看现有密码，则需要可逆加密与独立密钥管理，增加额外的保管和迁移要求。现有 UI 尚未据此改动，不能默认某一方案已经批准。推荐由用户选择后再正式实现。
